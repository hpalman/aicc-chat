## 개요

`ChatAgentService.checkAgentAvailability()` 메서드를 수정하여, Redis의 `chat:user-agent:{agentId}` Hash Table에서 `agentStatus`가 `WAITING`인 상담원만 조회하도록 개선했습니다.

### 개선 전 문제점

- 모든 온라인 상담원을 조회하여 가용성을 확인
- `agentStatus`가 `WORKING`인 상담원도 포함되어 잘못된 가용성 판단 가능
- 상담원이 "대기종료" 상태(`WORKING`)일 때도 가용한 것으로 판단될 수 있음

### 개선 후

- `agentStatus`가 `WAITING`인 상담원만 조회
- "대기" 상태인 상담원만 자동 배정 대상으로 판단
- 더 정확한 가용성 체크 가능

## Redis 키 구조

### 상담원 정보 저장 구조

**키 패턴**: `chat:user-agent:{agentId}`

**타입**: Hash

**Hash 필드**:
| 필드 | 타입 | 설명 | 예시 |
|------|------|------|------|
| `userName` | String | 상담원 이름 | "김상담" |
| `userId` | String | 상담원 ID | "agent01" |
| `loginTime` | String | 로그인 시간 (ISO-8601) | "2026-02-04T17:30:00" |
| `lastHeartbeat` | String | 마지막 하트비트 시간 | "2026-02-04T17:40:00" |
| `agentStatus` | String | 상담원 상태 | `WAITING` 또는 `WORKING` |

### agentStatus 값

- **`WAITING`**: 대기 중 (자동 배정 가능)
- **`WORKING`**: 업무 중 (자동 배정 불가)

```java
public Map<String, Object> checkAgentAvailability() {
    // 1. Redis의 chat:user-agent:{agentId} 키들을 조회하여 agentStatus가 WAITING인 상담원만 필터링
    Set<String> onlineAgentKeys = redisTemplate.keys(Constants.USER_AGENT_KEY + ":*");
    Map<String, String> waitingAgents = new java.util.HashMap<>(); // agentId -> userName

    if (onlineAgentKeys != null) {
        for (String key : onlineAgentKeys) {
            String agentId = key.substring((Constants.USER_AGENT_KEY + ":").length());

            // Hash에서 agentStatus 조회
            Object agentStatusObj = redisTemplate.opsForHash().get(key, "agentStatus");
            String agentStatus = agentStatusObj != null ? agentStatusObj.toString() : null;

            // agentStatus가 WAITING인 경우만 추가 ✅
            if ("WAITING".equals(agentStatus)) {
                // Hash에서 userName 조회
                Object userNameObj = redisTemplate.opsForHash().get(key, "userName");
                if (userNameObj != null) {
                    String userName = userNameObj.toString();
                    waitingAgents.put(agentId, userName);
                    log.debug("▶ WAITING agent found: agentId={}, userName={}", agentId, userName);
                }
            }
        }
    }
    
    // ... 나머지 로직
}
```

## 동작 흐름

### 전체 흐름

```
1. Redis에서 chat:user-agent:* 패턴의 모든 키 조회
   ↓
2. 각 키의 Hash에서 agentStatus 필드 조회
   ↓
3. agentStatus가 "WAITING"인 경우만 필터링
   ↓
4. 필터링된 상담원 목록 생성 (agentId -> userName)
   ↓
5. WAITING 상태인 상담원이 없으면 즉시 불가 반환
   ↓
6. 상담원이 배정된 방 개수 세기
   ↓
7. WAITING 상태인 상담원 중 3개 미만의 상담을 하고 있는 상담원이 있는지 확인
   ↓
8. 결과 반환
```

### 상세 흐름

```
checkAgentAvailability() 호출
   ↓
Redis KEYS chat:user-agent:*
   ↓
각 키에 대해:
   ├─ HGET chat:user-agent:{agentId} agentStatus
   ├─ agentStatus == "WAITING"?
   │   ├─ YES → HGET chat:user-agent:{agentId} userName
   │   │         → waitingAgents에 추가
   │   └─ NO  → 건너뛰기
   ↓
waitingAgents.isEmpty()?
   ├─ YES → available=false 반환
   └─ NO  → 상담 개수 확인 및 가용성 판단
```

## 주의사항

### 1. agentStatus 필드가 없는 경우

- `agentStatus` 필드가 없는 상담원은 필터링에서 제외됩니다.
- 로그인 시 기본값으로 `WORKING`이 설정되므로, 명시적으로 `WAITING`으로 설정해야 합니다.

### 2. 상담원 상태 변경

- 상담원이 "대기" 버튼을 클릭하면 `setAgentStatus(agentId, "WAITING")` 호출
- 상담원이 "대기종료" 버튼을 클릭하면 `setAgentStatus(agentId, "WORKING")` 호출
- 상태 변경 시 자동으로 가용성 체크가 업데이트됩니다.

### 3. 성능 고려사항

- `redisTemplate.keys()` 사용 시 프로덕션 환경에서는 성능 이슈가 있을 수 있습니다.
- 대량의 상담원이 있는 경우 `SCAN` 명령을 사용하는 것을 고려할 수 있습니다.
- 현재 구현은 소규모 환경에 적합합니다.

### 4. 동시성

- Redis Hash의 `agentStatus` 필드는 원자적으로 읽히므로 동시성 문제는 없습니다.
- 하지만 상태 변경과 가용성 체크 사이에 타이밍 이슈가 있을 수 있습니다.
